# 两小时自主维护与策略优化

2026-10-04 用户授权把原只读检查改为自动修复及策略优化。原systemd timer仍在东京时间每两个小时的20分触发，不补跑、不重叠。单次总上限55分钟；诊断20分钟、候选修复10分钟、测试/上线分别有独立时限。

## 每轮实际执行

1. 读取账本策略、暂停标记、未知订单、活动周期、inflight及systemd状态。恢复已启用但失败的面板、已启用但停止的交易timer；在安全条件下为过期心跳执行一次原有受风控约束的Paper周期。不会启用被手动禁用的timer。
2. 使用现有`Automation._evaluate`评估BTC/XRP参数。先只读获取资产规则，再获取周期及账本锁，避免网络等待阻塞交易。暂停、未知提交、配置未批准或已有活动周期时延期，不下单。若开始时延期，诊断完成后重试一次并保留前后审计；已经完成的评估不会重复消费验证样本。
3. Codex只读诊断当前源、策略和最近两小时证据，设置`repair_requested`。确认是软件缺陷才进入候选修复，正常Hold、上游真实行情无更新及样本不足不触发强行交易。
4. 在`/tmp/crypto-agent-repair-*`复制无凭据候选项目，使用Codex `workspace-write`与`approval_policy=never`。候选目录在生产Git祖先目录之外，不能把生产仓库推断成可写工作区。不复制.env、账本、通知配置、Git、venv。
5. 比较全部文件哈希及broker AST，封存原有测试。允许修改公开Coinbase读取、模型协议worker，以及Alpaca的get_bars/get_markets/get_market方法；可新增回归测试。禁止修改其他broker行为、风险/执行/自动化核心、配置和原有测试；最多六文件/150KB，禁止新依赖。候选broker方法不允许触及下单开关、客户端凭据或非GET请求。
6. 使用原Python环境、候选PYTHONPATH和去掉应用凭据的环境运行全部原有回归及新增测试、lint；失败就保留生产版本。
7. 检查生产代码及批准摘要没有漂移，取得共享部署锁，停止timer并等待当前周期自然结束。备份原代码、策略/policy和SQLite；不终止活动轮次。部署后自动生成`maintenance_revision`，绑定新的批准摘要，隔离前后优化样本，并保留已有较低的仓位倍数。
8. 重启受影响面板，释放面板控制锁，确保用户暂停按钮可用。遵守300秒最小间隔，运行一次原Paper服务验证，要求上线后新启动的真实周期产生至少一个有效策略决策，避免把旧周期、全币种阻断或systemd成功退出当成修好。通过后恢复timer。失败则暂停，活动轮次结束后可回滚代码/配置；不覆盖账本、不重放订单。如果仍有活动轮次，不在其运行中回滚代码，保留暂停和备份供核对。

## 策略调整边界

自动优化当前支持仓位倍数`1 → 0.75 → 0.5`，只能维持或降低当前倍数，不提高风险。继续要求至少146条有效连续样本、96条训练覆盖16小时、48条独立验证覆盖8小时、双方至少5次完整往返，以及原有收益改善/回撤门槛。真实查看过的验证后缀只使用一次；样本不足不调参。代码或来源修复后的数据重新积累。

仓位、单笔额度、日亏损、报价/分钟时效、分钟连续性、两次确认、成本覆盖、入场冷却等保护保留。没有自动放宽阈值，也不承诺盈利。人工暂停和日亏损停机保留；只有“连续三轮失败”的故障停机，且订单/活动状态清楚、已有通过回归的代码修复，才可重新批准并验证恢复。

## 审计与并发

每轮目录包含`recovery.json`、`optimization.json`、`report.json`、`maintenance.json`及候选/测试/部署/备份记录。失败还保留`failure.json`，诊断失败也不会取消已经执行的服务恢复和优化记录。最近汇总的`maintenance`记录实际动作，不再只有建议。

`runtime/deployment.lock`同时保护部署和GitHub同步，防止同步中间版本。`control.lock`仅在原子部署阶段保护面板控制；验证阶段释放，手动暂停优先。保持原检查静默通知行为。

Codex参数依据[官方非交互模式文档](https://learn.chatgpt.com/docs/non-interactive-mode)和已安装CLI帮助验证。全局Codex权限配置、网络、SSH、Tailscale、防火墙和凭据未改变。
